# Nested Crossplane + Flux desired-state preview

Two complete source snapshots, `before/` and `after/`, exercise the actual Flux,
Helm, and Crossplane render plugins. All changes originate in the two
`environments/*/platform.yaml` inputs. The chart, XRDs, Compositions, and Function
definitions are identical across snapshots.

## Generated artifacts

- [Open the self-contained HTML report](report.html)
- [Machine-readable rendered diff](diff.json)
- [Report overview screenshot](report-preview.png)

These artifacts were generated by the actual `gitops-preview` CLI, both gRPC
plugins, Crossplane controller v2.4.2, and upstream function-go-templating v0.12.0.
Both inventories rendered completely. The report was opened in Chrome and its
cluster filters, logical-resource search, unified diff, and split diff were
checked against the real output.

The inputs target **Crossplane controller engine v2.4.2** and the real
**function-go-templating v0.12.0**. Each of the four v2 XRDs explicitly uses
`scope: Namespaced`, defines a typed `spec.config` object, and selects a unique
Composition through `defaultCompositionRef`. Crossplane supplies the v2
`spec.crossplane` control fields; the example does not redefine them or use claims.
Every Composition has one Inline GoTemplate pipeline step using
`.observed.composite.resource.spec.config`.

## Source layout

Each snapshot is an independent repository-shaped directory:

```text
before/ or after/
├── .gitops-preview.yaml
├── clusters/
│   ├── staging/bootstrap.yaml
│   └── production/bootstrap.yaml
├── environments/
│   ├── staging/{kustomization.yaml,platform.yaml}
│   └── production/{kustomization.yaml,platform.yaml}
├── platform/
│   ├── kustomization.yaml
│   ├── namespaces.yaml
│   ├── definitions.yaml       # XPlatform, XApplication, XDatabase, XCache
│   ├── compositions.yaml     # Four matching pipeline Compositions
│   └── function.yaml         # Function named templating
├── app-config/settings.yaml  # Raw YAML with Flux substitution variables
└── charts/checkout/
    ├── Chart.yaml
    ├── values.yaml
    └── templates/resources.yaml
```

The config selects `clusters/staging` and `clusters/production` as separate
cluster roots and enables `helm`, `resolve-git`, `sort`, and `exclude-crds`.
Cluster identity keeps identical Kubernetes names in the two inventories separate.
XRDs are render inputs and remain visible; `exclude-crds` filters Kubernetes
`CustomResourceDefinition` objects, not `CompositeResourceDefinition` objects.

`GitRepository/example-repo` is in `flux-system` and uses `url: ./`, the preview
plugin's local source convention. Paths are relative to the selected snapshot
root. The chart is vendored, has no dependencies, and requires no external Git or
Helm chart acquisition. This URL is a local preview fixture, not a deployable
remote Flux Git URL.

## Resource chain

```text
GitRepository flux-system/example-repo (local snapshot)
└── Flux Kustomization flux-system/platform-root
    └── environments/<cluster>/kustomization.yaml
        ├── shared platform: namespaces + 4 XRDs + 4 Compositions + Function
        └── XPlatform apps/checkout
            ├── Flux Kustomization apps/checkout-app-config
            │   └── app-config/settings.yaml + postBuild.substitute
            │       └── ConfigMap apps/checkout-app-values
            │           └── values.yaml: replicaCount (HelmRelease valuesFrom)
            └── XApplication apps/checkout-app
                ├── HelmRelease apps/checkout-app
                │   └── GitRepository sourceRef namespace: flux-system
                │       └── charts/checkout (local vendored Helm chart)
                │           ├── Deployment apps/checkout-app
                │           ├── Service apps/checkout-app
                │           ├── Ingress + HPA apps/checkout-app (if expose)
                │           └── XCache apps/checkout-app-cache
                │               ├── ConfigMap ...-cache-settings (named)
                │               ├── ConfigMap policy (unnamed, logical key)
                │               └── ConfigMap ...-cache-debug (if debug)
                └── XDatabase apps/checkout-app-db
                    ├── RDS Instance apps/checkout-app-db
                    └── S3 Bucket apps/checkout-app-db-logs (if logs)
```

Discovery alternates between engines: Flux loads the platform; Crossplane emits
an application and a Flux Kustomization; Flux substitutes the values ConfigMap;
Crossplane emits a HelmRelease and database XR; Helm emits the workload and cache
XR; Crossplane emits the infrastructure and terminal ConfigMaps. The host follows
these dependencies to a stable desired inventory.

`postBuild.substitute` is Flux's inline substitution map (there is no literal
`postBuild.inline` API field). It supplies `APP_NAME` and string-valued
`APP_REPLICAS`. The ConfigMap contains numeric YAML `replicaCount`, consumed by
`HelmRelease.spec.valuesFrom`; inline Helm values deliberately do not override
replicas. Production after also uses this value for HPA bounds: **4–8 replicas**.

All XRs and controller resources have explicit names. The terminal policy
ConfigMap has only `generateName` and the stable
`gotemplating.fn.crossplane.io/composition-resource-name: policy` output key.
The real engine may assign an internal evaluation name; the preview captures
the desired output as an unnamed logical resource. Its logical identity comes
from the named cache parent and composition output key, not a fabricated live
Kubernetes name. Production's memory change should therefore be a modification
of this resource, not a delete/add pair.

## Before → after

| Input | Staging | Production |
| --- | --- | --- |
| Container image | `nginx:1.27.4` → `nginx:1.28.0` | Same release bump |
| Replicas | 1 → 2 | 2 → 4 |
| Workload size | `small` unchanged | `small` → `medium` (CPU/memory requests and memory limit) |
| RDS instance class | `db.t3.micro` unchanged | `db.t3.small` → `db.t3.medium` |
| RDS allocated storage | 20 GiB unchanged | 20 → 40 GiB |
| Cache capacity | 1 GiB unchanged | 1 → 2 GiB (policy max memory 1024 → 2048 MiB) |
| Exposure | Off | Off → on: adds Ingress for `checkout.example.test` and HPA |
| Logs | Off | Off → on: adds S3 Bucket |
| Debug config | Off | On → off: removes named debug ConfigMap |

The RDS and S3 resources use the namespaced Upbound AWS API groups
`rds.aws.m.upbound.io/v1beta1` and `s3.aws.m.upbound.io/v1beta1`. Their
`forProvider` fields describe representative desired infrastructure. They refer
to a `ProviderConfig` named `default`; no providers, credentials, observed cloud
state, or connection Secrets are needed for rendering. Database password
management is expressed through `manageMasterUserPassword: true`.

This is a **desired-state preview**, not evidence that a database or bucket
exists. Rendering runs the composition function locally and does not apply
manifests to Kubernetes or reconcile cloud providers.

## Run with the real engine and function

Prerequisites: Linux/amd64 for the engine download below, Go with automatic
toolchain selection, `curl`, `sha256sum`, and this repository's source checkout.
The host and both sibling plugins must be installed together. If already built,
use their directory as `bin` and skip the three toolkit build commands.

### 1. Build the toolkit and install the pinned runtime

Run from the toolkit repository root:

```bash
set -euo pipefail
bin="$HOME/.local/share/nested-crossplane-flux/bin"
mkdir -p "$bin"
go build -mod=readonly -buildvcs=false -o "$bin/gitops-preview" ./cmd/gitops-preview
go build -mod=readonly -buildvcs=false -o "$bin/gitops-preview-flux" ./cmd/gitops-preview-flux
go build -mod=readonly -buildvcs=false -o "$bin/gitops-preview-crossplane" ./cmd/gitops-preview-crossplane

# Install the controller engine, not the user-facing Crossplane CLI.
url=https://releases.crossplane.io/stable/v2.4.2/bin/linux_amd64/crossplane
curl -fL "$url" -o "$bin/crossplane-core"
curl -fL "$url.sha256" -o "$bin/crossplane-core.sha256"
expected=$(tr -d '[:space:]' < "$bin/crossplane-core.sha256")
printf '%s  %s\n' "$expected" "$bin/crossplane-core" | sha256sum --check --status
chmod +x "$bin/crossplane-core"
test "$("$bin/crossplane-core" --version)" = v2.4.2

# Actual upstream function binary matching the Function package version.
GOBIN="$bin" go install github.com/crossplane-contrib/function-go-templating@v0.12.0
```

### 2. Start the function in a dedicated terminal

```bash
bin="$HOME/.local/share/nested-crossplane-flux/bin"
"$bin/function-go-templating" --insecure --address=127.0.0.1:9443
```

Leave it running while rendering. The Function manifest names `templating` and
pins `ghcr.io/crossplane-contrib/function-go-templating:v0.12.0`. The trusted CLI
override below connects that name to the upstream binary, so this reproduction
uses neither a mock function nor a Docker runtime. Repository YAML and
annotations do not grant a runtime endpoint.

### 3. Inspect each snapshot

In a second terminal, from the toolkit repository root:

```bash
bin="$HOME/.local/share/nested-crossplane-flux/bin"
example="$PWD/docs/examples/nested-crossplane-flux"

"$bin/gitops-preview" render "$example/before" \
  --config "$example/before/.gitops-preview.yaml" \
  --crossplane --crossplane-engine "$bin/crossplane-core" \
  --crossplane-function templating=127.0.0.1:9443 --output json

"$bin/gitops-preview" render "$example/after" \
  --config "$example/after/.gitops-preview.yaml" \
  --crossplane --crossplane-engine "$bin/crossplane-core" \
  --crossplane-function templating=127.0.0.1:9443 --output json
```

### 4. Generate the actual HTML report

```bash
"$bin/gitops-preview" diff "path:$example/before" "path:$example/after" \
  --config "$example/before/.gitops-preview.yaml" \
  --crossplane --crossplane-engine "$bin/crossplane-core" \
  --crossplane-function templating=127.0.0.1:9443 \
  --html --html-open=false
```

The command prints the generated report location. Open that `index.html` in a
browser. To inspect machine-readable changes, run the same diff with
`--output json` in place of `--html --html-open=false`. These are directory
sources; no Git commits or fixture generator are required. Stop the function
with Ctrl-C when finished.

## Verified inventory and report

Counts include source/controller resources, all four XRDs and Compositions,
and composed outputs, including the unnamed policy ConfigMap:

| Inventory | Before | After |
| --- | ---: | ---: |
| Staging | 25 | 25 |
| Production | 26 | 28 |
| Total across clusters | **51** | **53** |

Every cluster has 4 named XRs, 1 HelmRelease, 2 Flux Kustomizations, 1 local
GitRepository, 2 Namespaces, 4 XRDs, 4 Compositions, 1 Function, 1 Deployment,
1 Service, 1 RDS Instance, and 3 baseline ConfigMaps (values, settings, unnamed
policy). Production before adds the debug ConfigMap. Production after instead
adds the Ingress, HPA, and Bucket.

Verified change counts: staging **6 modifications**; production
**11 modifications, 3 additions, 1 deletion**; combined **21 changed resources**
(17 modified, 3 added, 1 deleted). Unchanged definitions and Services belong to
the inventory but do not count as changed report resources.

The optional built-in policies classify the rendered Deployment image and
replica changes in both clusters and the added production Ingress. Their
deterministic label mappings are `image-update`, `capacity-change`, and
`needs-network-review`; no `fail-on` rule or AI assessment is enabled.
The report shows the unnamed production cache policy as one modified
logical ConfigMap, the named debug ConfigMap as deleted, and distinct staging
and production resource chains.
